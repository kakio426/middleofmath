## A2-4 발행·교사 리포트 구현 명세

- 발행본: `grade4-semester1@1.3.0`
- 범위: 승인된 5개 단원, 27개 단계, 54개 판단
- 교사용 오답 해석: 정답이 아닌 108개 선택지에 정확히 1개씩 연결
- 조회 키: `(set_key, version, judgment_id, choice_id)`
- 보안 경계: 오답 해석은 학생 콘텐츠 JSON과 학생·교사 정적 번들에
  넣지 않고, 교사 권한으로만 읽는 별도 DB 테이블에서 제공
- 반 요약: 신호를 단원별로 묶되 여러 단원에 걸친 fallback 신호는 한
  단원으로 오표기하지 않고 `단원 정보 없음`으로 분리
- 데모 선택: `?set=grade4-semester1`은 로컬 `VITE_DEMO_MODE=true`에서만
  작동하고 운영 모드의 콘텐츠 선택에는 영향을 주지 않음

DB는 발행 행마다 `diagnostic-integrity` gate가 있어야 한다. gate의
세트·목표 버전이 행과 같고, `valid=true`, 오류 0건이며 `policy`와
`enforced`가 일치해야 한다. 애플리케이션 발행 RPC뿐 아니라 직접 SQL
INSERT에도 같은 불변식을 적용해 다음 발행에서 우회가 다시 생기지
않도록 했다.

기존 DB에 gate 없이 남아 있던 발행본은
`202607310007_legacy_publication_gate_backfill.sql`이 세트·버전에
고정된 레거시 `warn` 증명으로 한 번 보정한다. 보정 직후 발행 행에는
gate가 반드시 있어야 한다는 CHECK 제약을 검증된 상태로 추가하고,
발행본 불변성 트리거를 다시 활성화한다. 신규 설치의 seed도 같은 범위
증명을 직접 넣으므로 깨끗한 설치와 기존 DB 업그레이드가 모두
성공한다.

## A2-2 규칙과 관계 구현 명세

Kiro CLI의 첫 제안은 성취기준 절을 잘못 연결해 폐기했다. 교육과정 원문을
다시 대조한 뒤 다음 세 기준으로 교정했다.

- `[4수02-01]` 다양한 변화 규칙을 찾아 설명하고 수나 식으로 나타내기
- `[4수02-02]` 계산식 배열에서 규칙을 찾고 계산 결과 추측하기
- `[4수02-03]` 등호로 크기가 같은 두 양의 관계를 식으로 나타내기

초4 범위를 넘는 일반항, 문자식, 혼합계산은 넣지 않는다. 다음 다섯
학습 단계를 direct·transfer 한 문항씩, 모두 10문항으로 관찰한다.

| 단계 ID | 학생에게 관찰할 행동 | 시각 표현 |
|---|---|---|
| `patterns-relations.number-rule` | 수 배열의 반복되는 곱셈 변화 찾기 | 수 배열 |
| `patterns-relations.figure-rule` | 도형 순서와 전체 개수·증가량 구분하기 | 도형 배열 |
| `patterns-relations.rule-as-expression` | 대응표의 모든 줄에 맞는 식 고르기 | 대응표 |
| `patterns-relations.calc-array-rule` | 고정된 수와 변하는 수를 구별해 결과 예상하기 | 계산식 배열 |
| `patterns-relations.equal-sign` | 등호 양쪽의 값이 같도록 두 자리 수 찾기 | 등식 |

시각자료에는 정답이나 규칙을 따로 저장하지 않는다. TypeScript·Zod·SQL
검증기가 제시값으로부터 하나의 답이 정해지는지 다시 계산하고, 표현
유형과 관계없는 필드·답 필드는 저장 단계에서 거부한다.

| `figure-transform.flip-left-right` | 좌우로 뒤집었을 때 방향·위치 변화 알기 | 세로축 기준 좌우 뒤집기 결과 판단 | 비대칭 표시가 있는 도형의 대응 위치 판단 | `[4수03-04]` |
| `figure-transform.flip-up-down` | 위아래로 뒤집었을 때 방향·위치 변화 알기 | 가로축 기준 위아래 뒤집기 결과 판단 | 비대칭 표시가 있는 도형의 대응 위치 판단 | `[4수03-04]` |
| `figure-transform.rotate` | 기준점을 중심으로 돌린 결과 알기 | 90도 또는 180도 돌린 결과 판단 | 시작 방향이 다른 도형의 회전 결과 판단 | `[4수03-04]` |
| `figure-transform.point-move` | 격자에서 점의 이동을 위치와 방향으로 설명하기 | 한 방향의 점 이동 설명 | 가로·세로 두 방향의 점 이동 설명 | `[4수03-05]` |

원문 재검증에서 `[4수03-05]`가 무늬 꾸미기가 아니라 평면에서 점의
이동을 설명하는 기준임을 확인해 Kiro 1차 제안의 무늬 단계를 폐기했다.
또한 이 기준에서는 꼭짓점 이동을 이용해 평면도형의 이동을 설명하지
않으므로, A점과 B점만 있는 독립 격자 문항으로 구현한다.

문항 어휘는 초4 학생이 수학 행동을 바로 이해하도록 다음 용어를
일관되게 쓴다.

- `오른쪽으로 2칸 밀기`
- `세로선을 기준으로 좌우 뒤집기`
- `가로선을 기준으로 위아래 뒤집기`
- `점을 중심으로 시계 방향으로 90도 돌리기`
- `A점에서 B점까지 오른쪽으로 4칸 움직이기`

`대칭이동`, `사상`, `변환행렬`, `반사`, `평행이동 벡터` 같은 상위
어휘는 학생용 문항에 쓰지 않는다. `반 바퀴`와 `180도`처럼 표현이
달라질 수 있는 경우에는 한 문항 안에서 기준 표현을 먼저 분명히 한다.

## 5. 단계별 진단 설계

각 단계에는 오개념 두 개를 둔다. 오개념 제목만 반복하는 것이 아니라
direct와 transfer의 실제 오답 선택지에 같은 오류 규칙을 각각 적용한다.

| 단계 | 오개념 A | 오개념 B |
|---|---|---|
| 밀기 | 이동 방향을 반대로 적용 | 이동 칸 수를 시작 칸까지 포함해 한 칸 틀림 |
| 좌우 뒤집기 | 도형을 그대로 옆으로 옮김 | 좌우가 아니라 위아래를 뒤집음 |
| 위아래 뒤집기 | 도형을 그대로 위·아래로 옮김 | 위아래가 아니라 좌우를 뒤집음 |
| 돌리기 | 회전 방향을 반대로 적용 | 중심을 고정하지 않고 도형 전체를 옮김 |
| 점의 이동 | 출발점과 도착점을 바꾸어 방향을 반대로 설명 | 출발 칸을 포함해 한 칸 크게 셈 |

근거 작성 규칙:

- 오답 근거는 `잘못 계산함` 같은 일반 문장이 아니라 실제 보이는
  결과와 연결한다.
- 예: `오른쪽으로 2칸`을 `왼쪽으로 2칸` 적용해 나온 위치를 선택했다.
- 좌표나 방향을 콘텐츠에서 계산할 수 있으면 선택지와 rationale을 같은
  원천 데이터로부터 산출한다.
- 두 오답이 우연히 같은 그림·같은 라벨이 되면 문항을 발행하지 않는다.
- 선택지는 정답 1개와 서로 다른 오답 2개여야 한다.
- 그림을 보지 않고 어휘 해석만으로 답이 갈리지 않게 문장을 짧고
  직접적으로 쓴다.

## 6. 시각자료 계약

TypeScript·Zod·SQL·React SVG에서 같은 좌표 규칙을 사용한다.

### 6.1 기본 원칙

- 장식 이미지나 생성형 이미지를 사용하지 않는다.
- 격자, 도형, 기준선, 중심점, 이동 화살표를 결정론적 SVG로 그린다.
- 그림의 실제 좌표가 문제의 이동 규칙과 일치해야 한다.
- 정답 그림을 prompt, 안내 문구, `aria-label`에서 먼저 설명하지 않는다.
- 선택지 썸네일이 꼭 필요한지 교사 승인 때 확정한다. 현행 선택지는
  텍스트 라벨이므로, 승인 없이 도메인을 다중 그림 선택지로 확장하지 않는다.
- 한 화면에 너무 많은 상태를 겹쳐 보여 주지 않는다. 시작 도형과 관찰에
  필요한 결과 또는 경로만 표시한다.

### 6.2 구현 종류

`grid-transform-diagram` 하나의 계약에서 다음 모드를 구분한다.

```ts
type GridTransformDiagramVisual = {
  kind: "grid-transform-diagram";
  mode: "slide" | "flip-left-right" | "flip-up-down" | "rotate" | "point-move";
  rows: number;
  columns: number;
  sourceCells?: Array<{ row: number; column: number }>;
  targetCells?: Array<{ row: number; column: number }>;
  sourceMarker?: { row: number; column: number };
  targetMarker?: { row: number; column: number };
  axisIndex?: number;
  center?: { row: number; column: number };
  direction?: "up" | "down" | "left" | "right";
  amount?: number;
  turn?: "clockwise" | "counterclockwise";
  points?: Array<{ label: "A" | "B"; row: number; column: number }>;
};
```

최종 필드와 조합 규칙은 구현 직전 타입·Zod·SQL을 함께 설계하며 다음을
강제한다.

- 모든 셀은 격자 범위 안에 있다.
- 셀은 중복되지 않고 연결된 도형을 이룬다.
- 비대칭 표식은 도형 안에 있고 뒤집기·돌리기 결과에서 함께 움직인다.
- `slide`에는 축이나 회전 중심을 지정하지 않는다.
- `flip-left-right`에는 세로 기준선, `flip-up-down`에는 가로 기준선을
  사용하며 이름과 화면 표현을 교차 검증한다.
- `rotate`에는 중심, 방향, 90도 단위의 회전량이 필요하다.
- `point-move`에는 서로 다른 위치의 A점과 B점만 허용하며 도형 셀을
  함께 넣지 못한다.
- `targetCells`를 보여 주는 모드는 정답을 그대로 노출하지 않는 판단에서만
  허용한다.
- 학생이 보게 되는 SVG와 `aria-label`은 보이는 사실만 설명한다.
